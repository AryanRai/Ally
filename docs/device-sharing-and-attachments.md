# Phone sharing and device attachments

Android's Share menu now offers Ally for text, images and files. The phone composer also has a **+** file picker. Shared content opens as a reviewable draft: choose a chat, edit the shared text or add a message, remove files, then press Send. Sharing alone never starts an agent. Private file copies and uploaded IDs survive process recreation and failed sends; successful receipt clears the draft. Binary attachments wait until an existing response finishes instead of silently becoming text steering input.

Limits: six files, 20 MiB each, 40 MiB combined; 12,000 message characters. PNG, JPEG, GIF and WebP are sent as image input with the correct format. Other files are supplied as explicit local attachment context to the selected native session. Retry IDs include text and ordered attachment IDs; changed content with the same ID is rejected. Unconfirmed sends retain their original chat and draft.

Phone and watch history show authenticated image previews and file cards. Tap an image for zoom/pan; the watch also has zoom buttons. Phone supports Android Share/save-a-copy, and files use a temporary FileProvider read grant to a compatible viewer. A watch needs a compatible installed viewer for non-image files. Missing or expired original native files cannot be recovered.

The bridge retains user images, MCP/tool screenshots, native Codex `imageView` files, image generation output, and existing absolute assistant Markdown file links. Tool screenshots currently use the agent's existing thumbnails; explicit local Markdown image files retain their original bytes. Real forwarded Codex approvals can include their supplied image blocks and recent same-turn tool screenshots. This does not create approvals or expand which native approvals the existing route forwards; existing answers, cancellation and expiry remain authoritative.

`POST /v1/attachments` uploads bounded raw bytes and returns an opaque descriptor. `GET /v1/attachments/<sha256>` requires the paired bearer token and cannot accept a local path. Device fetches restrict URLs to the configured bridge, disable redirects, bound downloads and use private caches. Assets are stored in desktop user data under `device-attachments`; no remote image fetching or new model loop is introduced.

Validation: TypeScript; full desktop suite 276/276 before the final native-image conversion, then all 13 affected bridge/media/history/event tests after it. Phone 14/14 and watch 28/28 unit tests, both APKs and phone lint pass. Existing watch lint has the previously documented masked pairing-token warning. Mocked integration covers upload authentication, inert upload, exact-session image input, idempotent retry/conflict, screenshot transport and real approval cancellation. No model verification requests, recording or approval taps were used.

Installed APKs retain pairing/preferences. The isolated desktop build is `%LOCALAPPDATA%/Ally/builds/device-attachments-20261018/glass-pip-chat`; it preserves the separately deployed pill renderer byte-for-byte. Shared `dist` and concurrent source remain untouched. Live Android text/image share review and discard were verified with synthetic content; no content was sent.

Live verification also confirmed 12 native screenshots in the current Codex history, authenticated cloud downloads with exact declared byte counts, phone image viewing, and the actual watch image viewer/zoom controls. Restored the watch’s original selected chat and orb. Both devices reconnected and cloud speech/status were ready. A Windows compositor crash interrupted the first post-build session; Ally was relaunched and the checks repeated successfully. Final running main process: 28248.
