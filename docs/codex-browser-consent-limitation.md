## Earlier ecosystem-specific audit

The ecosystem MCP continuation handler imports presentEcosystemMcpElicitation. Its onReply callback resolves a local deferred promise with the user decision. With recipientThreadId it mounts a React request panel through tcr/ncr; otherwise it opens a local modal. These controls are not part of the conversation state's requests array.

The existing thread-follower-submit-mcp-server-elicitation-response route resolves native app-server conversation requests by requestId. It cannot resolve a standalone ecosystem UI deferred promise. Ally must not manufacture a matching request ID, reuse consent, inject into that UI, patch installed Codex, or automate a security approval.

No supported bridge for observing/answering the private ecosystem deferred was found in the local coordination methods or available app tools. This is not a finding that every Chrome consent uses that path. Reloading cannot add an absent callback route, but a restart may affect stale owner state; that is a separate issue requiring verification. No pending request was observed in the inspected older native feed; this does not establish absence in the current owning transport.

Needed upstream: authenticated event for the real ecosystem consent including originating chat, stable request identity and revocation; supported response API preserving native validation and user-selected scope. Once provided, Ally can mirror it through its existing InteractionBroker and phone/watch notifications.

Existing supported path: native app-server command/file/permission/MCP-form approvals received by Ally. Private ecosystem deferred forms remain outside that coverage. When an actual request is absent from Ally, the original Codex dialog remains the available human decision surface; do not invent an Ally decision or imply a pending Allow prompt exists without observing it.

No Codex restart, permission change, installed app modification or fabricated decision performed during this investigation.

Follow-up audit: inspected full Codex client-coordination method table, native main-process request registration, ecosystem requestState/inputResponses continuation loop, and externalRequests references.
