# Change access while a reply is running

On the phone, tap the access label above the composer. On the watch, open Settings → Chat permissions. Read only, Edit files, and Full access remain selectable while a reply is running.

Ally waits for the backend response before changing the displayed selection. Codex uses its existing native thread permission update route, including the active turn identity when available. Managed app-server runs use `thread/settings/update`. No message is submitted, interrupted, restarted or replayed by an access change. Already running tools retain the access under which they started; browser and other required confirmations remain separate.

Claude's current one-shot CLI connection cannot change its permission mode live. Its selector saves the choice for the next message, including subsequent queued follow-ups, and explicitly says the current reply keeps its existing access. A Codex version that explicitly rejects the live settings method also receives this label. Timeouts and connection errors remain unconfirmed failures, without an automatic retry or claimed success.

The authenticated device route is `POST /v1/chats/:id/access`, with `{ "permission": "readonly" | "edit" | "full" }`. It rejects browser Origins and concurrent changes for the same chat. The response includes the confirmed selection and `current_reply` or `next_message` scope. Reading a chat never changes access.

Validation uses synthetic RPC/native owner fixtures and HTTP bridge tests, plus TypeScript checks and both Android builds/unit suites. No live model prompt or real permission decision is generated by these checks.
