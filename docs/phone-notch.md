# Optional phone notch and phone-control glow

Ally has an independent built-in phone module at `wear-app/phone/.../notch`. It is off by default. It does not load executable plugins and does not require dynamicSpot. The normal phone chat, assistant, microphone, route picker, attachments, queue, speech and watch connection keep their existing implementations. No desktop/watch sources or account settings are changed by this module.

## Setup

Phone **Ally → Settings → Phone notch**:

1. Enable the notch. It reuses the already-enabled Ally Accessibility overlay, or the user can grant **Display over other apps** in Android's own settings. Neither grant is performed automatically.
2. Allow notifications if needed. A separate low-priority ongoing notification has Settings and Stop; Stop turns the saved notch preference off. This foreground service's special-use declaration is the persistent, explicitly enabled status overlay. Store distribution still needs the usual foreground-service review.
3. Selected-app notification and now-playing support are separate switches, initially off. Android notification access and a per-app selection are both required. None are selected by default. The existing media-handoff listener and its permission/opt-in are unchanged.

The notch survives normal activity navigation, not Android force-stop or every vendor battery policy. There is no boot receiver, permission auto-grant, battery-optimization exemption, wake/unlock action or full-screen permission request added. If Android refuses the optional foreground service, normal Ally still works; reopen the setting after granting the listed prerequisites. No new permission is required solely for the control edge glow.

## Phone UI and shared decisions

The default idle view is a transparent camera ring, not a wide black pill. It uses a 44dp camera-area touch target and a 24dp drawn ring (size adjustable 80–130%). Tap once for a 48dp-high status pill below the camera; it returns to the ring after8seconds. Tap the status pill for the full panel. Pending decisions change the indicator, never automatically expand it. The settings also offer an always-visible status pill and ±32dp horizontal/vertical camera alignment. Geometry uses current display metrics, measured cutout bounds and system-bar insets. It repositions on changed geometry/rotation and stays within the available window. Portrait top cutouts anchor the pill; side cutouts in landscape do not incorrectly anchor it off-screen. The temporary status row sits below the camera hole; the idle ring has no filled background or text block. The actual window is only the pill's bounds, non-focusable/non-touch-modal; the rest of the screen is not a touch interceptor.

The second tap opens a native floating panel, capped at360dp wide and60% of display height (up to520dp), with normal Android IME handling. The panel and all notch settings now use Ally Compose surfaces, saved accent, Geist body type, Tanker wordmark, mono labels and rounded outline controls rather than legacy Android widgets. Outside-tap, Back and Collapse return to the compact pill. Swipe the pill horizontally/up to hide ordinary status for30seconds. A pending real decision remains reachable. Hold opens its settings. There is no second live notification for each agent/request and no copy of approval state.

Priority: real broker questions/approvals → validated phone-control session → listening/transcription/speech → public work → selected local phone events → selected-chat/connection preview. Counts come from Ally's existing surface feed/inbox. Disconnected state is labelled, stale cached activity is not presented as live work. The expanded panel provides public preview, the existing full phone question/approval card (including options/free text), Stop control, Stop response, Stop audio and links to the original chat/assistant. Voice recording, queue/steer, attachments and speech remain in the full existing chat/assistant rather than a second composer. No reasoning or tool arguments are extracted into a new stream.

`DeviceInteractionCard`, `ChatApproval`, `DeviceLink.answerInteraction` and the existing conversation `answer` method retain real request IDs, expiry, connection/session binding, sending state and acknowledgement handling. A decision answered on another surface changes the same inbox/state and disappears here too. Opening/collapsing the notch never submits a prompt or approval. Desktop-only decisions remain on their supported surface.

Both panel and compact notch are secure windows; locked/screen-off state hides the compact overlay. The panel refuses a locked launch and checks for lock while visible. Permission/SystemUI/installer/settings window events from the existing Accessibility service suppress control/notch overlays so they do not cover security setup. When the supported control screenshot path runs, both added visual overlays are removed synchronously before capture and restored only if still eligible. Existing Accessibility-window tree exclusion remains unchanged.

## Control edge glow

`ControlVisualState` is set only after `ControlGrant.parse` and the existing service/grant checks succeed. Request presentation alone cannot light it. Phone-control operations increment/decrement the validated grant's in-flight count; a short650ms visual pulse makes brief actions visible without claiming a tool is still running. Idle grants have a dim cyan outline. Actual action pulses are brighter, with reduced-motion, system animation-off and battery-saver support. The edge uses an untouchable, non-focusable `TYPE_ACCESSIBILITY_OVERLAY` with no filled interior or input callbacks. The persistent existing Stop notification remains intact, and the notch panel adds another explicit Stop for the same grant.

Expiry, disconnect, Stop/revoke, service interruption/unbind/destruction clear the real visual state. Lock/screen-off and protected windows hide the glow; control performs refuse a locked screen. No new grant is created when it returns. Screenshot hiding never creates or extends control. The saved **Phone-control edge glow** switch works even when the notch is disabled.

## Reference analysis and feature matrix

The user-supplied dynamicSpot3.00 reference (16,800,218bytes; package `com.jamworks.dynamicspot`, versionCode200145) was inspected statically, never installed/repackaged/modified. JADX1.5.6 was downloaded from its [official release](https://github.com/skylot/jadx/releases/tag/v1.5.6), with the GitHub asset SHA256 digest verified. It generated sources/resources under gitignored `.local/reference/dynamicspot`. Decompilation reported19 method errors, so this is an inventory of observed API/behavior, not a claim of complete source recovery. No rival source, artwork, strings or branding were imported into Ally, and no paid gates were changed.

Reference manifest and first-party decompiled classes inspected: `NotificationObserverSpot` (NotificationListenerService, notification post/remove, active MediaSessions, charging/screen broadcasts, timer app handling and optional Bluetooth information) and `OverlayServiceSpot` (AccessibilityService, TYPE_ACCESSIBILITY_OVERLAY numeric2032, multiple compact/expanded views, gestures, configuration changes and teardown). These established Android integration categories only. Ally geometry, state policy, rendering, controls and lifecycle are independently written against its own models.

| Category observed in reference | Ally implementation | Limit / permission |
|---|---|---|
| Cutout pill, expand/collapse and gestures | Independent camera/inset-aware compact native window and floating native panel | Overlay/Accessibility must already be granted; physical cutout/touch/IME acceptance pending |
| General notifications | Local opt-in listener, explicit selected apps, bounded24 event state,2minute expiry, open original PendingIntent only on explicit tap | Own/secret/security/auth/call/service/system/transport notifications excluded. Titles hidden unless separately enabled; no bodies/replies/actions harvested, no phone data sent to PC |
| Media session controls | Selected app playing/paused title, real MediaSession play/pause on explicit tap | Fresh session queried locally; disappears on removal/revocation/disable. Existing media handoff untouched |
| Timers/alarm notifications | Ordinary allowed app notices; countdown only when notification explicitly supplies show-chronometer + count-down + future `when` within24h | No guessing from alarm text, inaccessible custom timer layouts stay ordinary notices; no alarm creation/snooze/dismiss automation |
| Charging/battery | Separate opt-in sticky battery broadcast, actual charging percentage | No battery exemption/settings write; no private Bluetooth battery reflection |
| Call controls/contact identity | Deliberately not implemented | No contacts/phone-state/call-answer permissions added |
| Bluetooth/headset, volume, hardware indicators | Not implemented in this increment | No extra Bluetooth/audio access requested for the notch |
| Agent/chat/questions and control halo | Ally-native public state and exact existing request broker; validated-grant halo | No reference counterpart needed; no fake Allow UI, thought stream or new agent loop |
| Startup/battery/system tuning | Existing user-started foreground connection plus optional notch service | No boot receiver, WRITE_SETTINGS/WRITE_SECURE_SETTINGS, sensitive-notification privilege, camera, contacts, ads or wake-lock permission added by the notch |

Android references: [WindowManager overlay types and flags](https://developer.android.com/reference/android/view/WindowManager.LayoutParams), [notification listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [foreground special-use services](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use).

## Validation and delivery

Pure regression coverage includes priority/expiry/deduplication, feature-off/lock/screen-off/expanded hiding, snooze versus unanswered decisions, portrait/left-hole/landscape/tiny-window geometry, invalid metrics, notification app/privacy restrictions, explicit chronometer evidence and validated-grant/action lifecycle. Existing phone suites cover actual request parsing, decision closure, speech queue/capture/send, timeline and handoff. Build/lint/install evidence and exact APK hash are recorded in `.local/phone-notch/validation.json` after final validation.

No real phone control, native permission decision, user message, private screen capture or microphone recording is performed for a synthetic test. The normal phone-control tool intentionally refuses Ally itself; no ADB/UIAutomation substitute is used to work around that. ADB is used only for authorized APK replacement/identity, installed-package hash and assistant-binding checks. Physical visuals/touch-through/rotation/IME, cross-surface real decision closure and action glow still need user acceptance; tests and an installed APK are not that proof. Phone install uses `-r` and preserves pairing/preferences. Notch initially stays off; existing Android setup and opt-ins are user-owned. No desktop restart or Git publication requested/performed.
